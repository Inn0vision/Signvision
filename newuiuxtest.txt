# 4. MASTER ALIGNMENT AUDIT

THIS IS A CRITICAL PRIORITY.

Inspect every major screen and reusable component for accurate, consistent alignment.

## 4.1 Horizontal alignment

Verify:

- The left and right edges of related content align consistently.
- The header's content follows the correct content grid.
- The avatar stage is centered or intentionally positioned.
- The translation composer aligns with its intended content area.
- The word/sentence selector aligns with the composer where appropriate.
- Gloss-token containers follow the correct content boundaries.
- History items align with their section headings.
- Related action buttons follow a consistent baseline.
- Icon and text combinations are vertically centered.
- Desktop panels align to consistent column boundaries.
- Cards, dialogs, dropdowns, and sheets have deliberate content padding.
- Dividers and borders do not appear randomly offset.

Do not force every element to have the same width when it serves a different purpose. Use a consistent layout grid while preserving the intended visual hierarchy.

## 4.2 Vertical alignment

Check:

- Header height and internal alignment.
- Distance between the header and primary content.
- Avatar positioning within its stage.
- Space between the avatar, gloss information, and playback actions.
- Mode selector and composer placement.
- History section spacing.
- Vertical centering of icons within controls.
- Button-label alignment.
- Input text alignment, including multiline text.
- Dropdown anchoring and menu positioning.
- Dialog title, body, and action-button alignment.
- Vertical spacing across loading, empty, success, and error states.

Correct inconsistent spacing between related components.

Do not solve one misalignment by introducing an arbitrary margin that breaks another breakpoint.

## 4.3 Spacing consistency

Audit all important spacing values against the established design tokens.

Look for:

- Inconsistent horizontal padding.
- Unnecessary large gaps.
- Components touching when they should have breathing room.
- Overcrowded sections.
- Different gaps between visually equivalent controls.
- Unintentional differences between similar cards.
- Excessive padding on small phones.
- Excessive empty space on desktop.
- Repeated borders that make the screen feel fragmented.
- Overlapping shadows or inconsistent radii.

Use shared design tokens and layout relationships where practical.

When correcting an issue, fix its actual source instead of accumulating local overrides.

## 4.4 Visual hierarchy and balance

Ask the following while examining every rendered screen:

- Is the 3D avatar clearly the main visual attraction?
- Can the user quickly identify where to enter a word or sentence?
- Is the active translation mode immediately obvious?
- Are primary actions more prominent than secondary actions?
- Is the history area taking too much space?
- Does the interface have excessive cards or containers?
- Are important labels readable at ordinary viewing distances?
- Are glass effects making text harder to read?
- Does the interface look intentionally designed rather than mechanically assembled?
- Is there a clear visual path from input to translation to avatar playback?

Fix any imbalance that makes the screen confusing, cluttered, or awkward.

# 5. MOBILE RESPONSIVENESS AUDIT

Mobile must be verified separately from desktop.

Test these web viewport sizes where the web application is available:

| Test case | Width | Height |
|---|---:|---:|
| Very narrow phone | 320 | 568 |
| Small phone | 360 | 640 |
| Standard phone | 390 | 844 |
| Large phone | 430 | 932 |
| Small tablet / constrained layout | 600 | 800 |
| Tablet portrait | 768 | 1024 |
| Tablet landscape | 1024 | 768 |

These are CSS viewport dimensions for web testing, not a claim that every physical device has identical usable dimensions.

For native mobile, use the available actual emulator or device configurations and test equivalent constrained screen sizes where supported.

## 5.1 Small-screen integrity

At every narrow viewport, verify that:

- The complete primary workflow fits the available space or scrolls appropriately.
- Header controls are not clipped.
- The avatar is not unintentionally compressed.
- The composer remains usable.
- Mode controls are not cut off.
- Text and icons do not overlap.
- History does not push primary controls beyond usability.
- Gloss tokens wrap cleanly.
- Floating controls do not cover important content.
- No unintended horizontal scrolling occurs.
- No controls render outside the viewport.
- No fixed-height region truncates essential content.

Do not solve small-screen issues simply by shrinking every component.

Preserve a comfortable hierarchy and reduce secondary content before making essential controls difficult to use.

## 5.2 Safe areas and system interfaces

For native mobile, verify:

- Status bar and top safe-area insets.
- Camera notches and display cutouts.
- Bottom gesture/navigation areas.
- System navigation bars.
- Device orientation changes.
- Safe placement of floating and bottom-anchored controls.

Do not assume one hardcoded bottom offset works on all phones.

Avoid double-applying safe-area padding, which can create unnecessary gaps.

## 5.3 Keyboard and composer behavior

This is a mandatory functional test.

Test:

1. Opening text input when the keyboard is hidden.
2. Opening the keyboard on a short screen.
3. Entering multiline text.
4. Switching from word to sentence mode.
5. Opening autocomplete.
6. Selecting a suggestion.
7. Dismissing autocomplete.
8. Submitting a translation.
9. Dismissing the keyboard.
10. Reopening the input after a previous translation.
11. Scrolling while the keyboard is present, where supported.

Verify that:

- The focused input remains visible.
- The composer moves or resizes appropriately.
- The keyboard does not conceal the primary action.
- The dropdown is not clipped or positioned off-screen.
- Text is not lost during layout changes.
- The screen does not jump unexpectedly.
- The user can still access any relevant controls.
- Dismissing the keyboard does not leave unexplained blank areas.

Use the appropriate native keyboard-handling mechanism and web behavior for the actual platform. Do not assume the same implementation works identically on iOS, Android, and browsers.

## 5.4 Scrolling and overlapping

Inspect all scrollable areas.

Look for:

- Nested scrolling conflicts.
- Multiple competing scroll containers.
- Unreachable history entries.
- Scrollbars appearing in inappropriate places.
- The bottom composer covering content.
- Menus rendering behind other layers.
- Unintended scroll locking.
- Content disappearing after orientation changes.

The floating composer must never make the final history item or another essential control permanently inaccessible.

# 13. VISUAL ITERATION: INSPECT, FIX, RE-RENDER, RECHECK

THIS IS THE CORE OF THE TASK.

Do not perform one inspection and then immediately declare completion.

Use the following iterative process:

### Iteration 1: Baseline inspection

Launch the current application where possible.

Capture or inspect its actual rendered appearance on representative mobile and desktop viewports.

Identify the most significant issues with:

- Alignment.
- Spacing.
- Responsive composition.
- Typography.
- Overflow.
- Component consistency.
- Avatar integration.
- Interaction behavior.

### Iteration 2: Correct the layout foundations

Fix shared design tokens, parent layouts, flex or grid constraints, width limits, spacing relationships, and responsive breakpoints.

Where multiple screens share the same defect, fix the shared source rather than patching each instance separately.

### Iteration 3: Correct component-level defects

Fix the composer, selectors, avatar stage, gloss tokens, history, buttons, overlays, and other affected components.

Verify keyboard and safe-area behavior rather than relying on static appearance.

### Iteration 4: Re-render and compare

Run the application again and inspect the corrected output.

Check whether:

- The original defect is actually fixed.
- Other screen sizes remain correct.
- Shared components have not regressed.
- Keyboard behavior is still correct.
- The avatar has not been damaged.
- Spacing remains consistent throughout the interface.

### Iteration 5: Test edge cases

Inspect narrow viewports, large text, long content, empty states, open menus, keyboard visibility, and constrained desktop layouts.

Fix any new issue revealed by these tests.

### Iteration 6: Final regression verification

Rerun relevant build, type, lint, and functional checks after the final changes.

Inspect the actual final version, not a screenshot produced before the most recent edits.

Repeat this cycle as many times as needed until all critical and high-priority issues that are reproducible and fixable within the available environment have been corrected.

Do not introduce new design features merely to demonstrate activity.

Concentrate on measurable quality improvements and preserve the existing architecture.

# 14. DEFECT PRIORITY AND ACCEPTANCE RULES

Classify detected issues by severity.

**Critical:** Application cannot launch, core translation workflow is broken, the avatar integration is broken, or important user actions are inaccessible.

**High:** Composer is unusable, content overlaps, essential controls are clipped, mobile layout is broken, web content overflows, or major accessibility interactions fail.

**Medium:** Noticeable alignment errors, inconsistent spacing, broken secondary interactions, poorly positioned menus, or substantial typography inconsistencies.

**Low:** Small decorative inconsistencies, slight differences in shadows, or minor polish defects that do not affect usability.

Fix critical and high-priority issues first. Address medium and low-priority issues during the refinement passes wherever feasible.

A successful build alone is not acceptance.

A screenshot that looks good at one resolution alone is not acceptance.

A checklist with no actual implementation corrections is not acceptance.
