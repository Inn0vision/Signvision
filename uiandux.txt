The new visual identity must be consistent across screens, components, and platforms.

Do not style every component independently. First create a design system, then build the screens from it.

Create an immersive, premium, calm, modern AI accessibility application.

The aesthetic should combine:

- Deep midnight backgrounds.
- Refined emerald and cyan accents.
- Carefully layered surfaces.
- Consistent typography.
- Generous negative space.
- A prominent 3D signing stage.
- Smooth, intentional interactions.
- Clearly structured controls.
- Minimal but meaningful decoration.

Avoid:

- Generic dashboard layouts.
- Default Material Green utility-app aesthetics.
- Excessive neon effects.
- Gaming-inspired visual clutter.
- Oversized gradient backgrounds.
- Unnecessary cards around every element.
- Thick decorative borders.
- Excessively rounded controls everywhere.
- Randomly positioned floating elements.
- Dense, rigid, vertically stacked sections.
- Icons without clear meaning.
- Inconsistent margins and padding.

The final application should look designed as one cohesive product.

## 4.2 Centralized color system

Use the following starting palette and refine it during implementation:

- Main background: #07080D
- Secondary background: #0B0E14
- Main elevated surface: #111722
- Secondary elevated surface: #171E29
- Primary accent: #10B981
- Secondary accent: #22D3EE
- Primary text: #F5F7FB
- Secondary text: #A6B0C0
- Subtle borders: translucent white with carefully controlled opacity
- Error: accessible red
- Warning: accessible amber
- Success: accessible emerald

Create semantic tokens rather than applying raw hex colors throughout the application.

Include tokens for:

- Backgrounds and surfaces.
- Primary, secondary, and tertiary text.
- Primary and secondary actions.
- Focus, selection, and hover.
- Active, disabled, loading, and error states.
- Borders and dividers.
- Overlay surfaces.
- Elevation and shadows.
- Animation durations and easing.
- Spacing and radii.

Avoid green text on green backgrounds or cyan accents that damage readability.

## 4.3 Typography

Establish a complete typography scale.

Define consistent styles for:

- Brand and page headings.
- Section headings.
- Input and entered text.
- Buttons and action labels.
- Gloss tokens.
- Supporting descriptions.
- Error and permission messages.
- Status indicators and metadata.

Choose appropriate fonts based on existing project assets, platform support, and performance.

Use consistent font weights, line heights, and text alignment. Avoid unnecessary uppercase labels and excessively small descriptions.

Support system text scaling and long localized strings without clipping critical content.

## 4.4 Spacing and alignment system

THIS IS ONE OF THE HIGHEST-PRIORITY REQUIREMENTS.

Every major screen must have a consistent alignment system.

Define a spacing scale based on a deliberate grid, such as 4, 8, 12, 16, 24, and 32 logical pixels or points where appropriate.

Use shared tokens for spacing, content padding, gaps, section separation, and component dimensions.

Do not use arbitrary margins and padding independently in every file.

Every related element must line up intentionally:

- Header title and surrounding controls.
- Main content boundaries.
- Avatar stage.
- Translation composer.
- Mode selector.
- Gloss-token area.
- History section.
- Action toolbar.
- Desktop side panels.
- Dialog content and action buttons.

Align related edges to consistent guides. Keep related elements evenly spaced. Make the visual hierarchy obvious through size, weight, spacing, and placement rather than a mixture of random colors and borders.

Use flex layouts, grids, measured content widths, and predictable constraints. Use absolute positioning only when there is a clear reason, such as a genuinely floating composer or anchored overlay.

When using absolute positioning, account for safe areas, keyboard movement, scrolling, and content overlap.

Use responsive sizing rather than fixed dimensions where practical.

Make the layout look intentional on both narrow and wide screens. Do not simply reduce the desktop layout until it fits a phone.

## 4.5 Surface treatment and glassmorphism

Apply glass-like styling only where it makes the experience better.

Appropriate places may include a floating composer, a small contextual overlay, or a compact action panel.

Use soft borders, subdued transparency, and subtle shadows.

Do not apply blur indiscriminately to large areas. Avoid multiple overlapping glass panels that create visual noise or reduce performance.

Check the actual result over the real avatar rendering.

If transparent integration is not technically supported, use a compatible, well-matched dark surface instead of creating visible rectangular edges or unstable rendering.

# 5. PHASE FOUR: REDESIGN THE MOBILE APPLICATION

Mobile must be a first-class experience built around reachability, legibility, responsiveness, and the 3D signing avatar.

## 5.1 Overall screen composition

Remove the feeling of a rigid vertical stack of unrelated rows.

The screen should establish a clear hierarchy:

1. A compact header.
2. A visually dominant avatar stage.
3. Translation-related content and playback feedback where relevant.
4. A compact and well-aligned mode selector.
5. A floating, reachable translation composer.
6. Recent history and secondary actions in positions appropriate to the current state.

This is a compositional guideline, not permission to force every element onto the screen simultaneously.

Use the available viewport intelligently. Expand, collapse, or reposition supporting content when appropriate.

The avatar must receive sufficient space without making the input or other main controls hard to reach.

Do not hide essential functionality merely to create a cleaner screenshot.

## 5.2 Header

Create a compact, polished SignVision header.

Include only appropriate, functional controls such as:

- Brand identity.
- A concise page title or contextual label.
- Relevant settings or existing navigation.
- A meaningful status indicator when necessary.

Avoid redundant branding, unnecessary profile controls, oversized headers, and decorative icons with no behavior.

Align the header with the main content edges and respect the device's status bar and safe-area insets.

## 5.3 Avatar stage

The 3D avatar is the central product feature.

Give it a generous, visually dominant stage that feels integrated into the native application.

Implement appropriate states for:

- Initial loading.
- Avatar ready.
- Translation requested.
- Animation loading.
- Playback in progress.
- Paused playback, if supported.
- Completed playback.
- Playback failure.
- Missing animation assets.
- Recoverable network errors.

Render only states grounded in the actual application lifecycle.

Use an appropriate background treatment, balanced empty space, and careful sizing across phones, tablets, and orientation changes.

Playback buttons must call the existing playback implementation if supported. Do not create decorative controls that do nothing.

If actual synchronization data exists between gloss tokens and animation progress, use it. Otherwise, do not falsely present individual words as synchronized with hand movements.

Maintain the stability of the WebView and avoid unnecessary reloads.

## 5.4 Floating translation composer

Redesign SearchBar.tsx, or the equivalent actual component, into an ergonomic and visually polished composer.

It must support the existing input flow and any confirmed implemented functionality:

- Text entry.
- Multiline sentences.
- Word and sentence modes.
- Autocomplete and suggestions.
- Microphone or speech-recognition input.
- Submission.
- Editing and clearing text.
- Validation.
- Loading and processing feedback.

Use a well-structured, rounded surface, clear typography, restrained elevation, and a distinctive primary action.

Place it in the lower reachable zone of the mobile screen when appropriate, but do not obscure the avatar's important content, gloss information, history, or system navigation.

The composer must not simply use absolute positioning with a hardcoded bottom offset.

Correctly account for:

- Safe-area insets.
- Keyboard visibility and height.
- Device orientation.
- Multiline content.
- Small screen heights.
- Text scaling.
- Scrollable content.
- Focus changes.
- Autocomplete overlay placement.

When the keyboard opens, keep the current input visible and usable.

Preserve entered text when a permission request is denied or speech recognition fails.

Autocomplete must appear in a usable position, with sensible scrolling, dismissal, and selection behavior.

Avoid jumping layouts, clipped dropdowns, duplicated submission handlers, and inaccessible controls.

## 5.5 Word and sentence selector

Make Word and Sentence modes immediately recognizable.

Use an elegant segmented control or another suitable, well-researched native component.

It should have:

- A clearly distinguishable selected state.
- Adequate touch targets.
- Consistent horizontal alignment.
- Good contrast.
- Keyboard or screen-reader support where relevant.
- Predictable behavior when switching modes.

The selected mode must remain connected to the actual application state.

Use the true existing translation semantics and validation rules. Do not create a second independent state that disagrees with the primary mode.

## 5.6 Microphone workflow

Voice input should be an optional convenience, never a barrier to text translation.

When permissions are missing, explain the purpose of microphone access and request it at a relevant moment.

When access is denied:

- Keep text input usable.
- Provide a clear explanation.
- Offer an appropriate recovery path.
- Allow the user to continue without voice input.

When speech recognition starts, show the real recording state.

Handle recognition completion, empty results, cancellations, errors, repeated taps, and denied permissions.

Do not simulate recording or pretend to recognize speech when the underlying feature has failed.

Use clear textual feedback as well as visual indicators.

## 5.7 Gloss-token presentation

Make gloss tokens clear, readable, and visually related to the active translation.

Use consistent token spacing, line wrapping, typography, and active-state styling.

Avoid an uncontrolled collection of brightly colored pills.

Use restrained emerald and cyan highlights only where appropriate.

Animate additions and layout changes gracefully. Avoid making the text jump when a sentence produces many tokens.

Respect reduced-motion settings.

If the application provides actual playback timing information, use it to indicate the active token accurately. If it does not, provide honest playback-level feedback rather than fabricated synchronization.

## 5.8 Recent history

Replace rigid history rows with a design that suits the available space.

Consider a compact recent-history list or horizontally scrollable set of items, provided it remains accessible and practical.

Support the existing capabilities for reopening, reusing, or replaying entries wherever those capabilities already exist.

Do not make history larger or more visually prominent than the primary translation interaction.

Provide meaningful empty, loading, and overflow states.

Avoid excessive nested scroll containers and ensure each scroll area behaves predictably.

## 5.9 Secondary actions and navigation

Place secondary controls in a logical toolbar, accessible menu, or suitable bottom sheet.

Keep frequently used controls immediately discoverable.

Do not bury primary workflows behind several menus.

Preserve all existing navigation and functional actions.

### PHASE FOUR EXIT GATE

The mobile screen must be visually coherent, usable with one hand where practical, safe around the keyboard, and functional across small and large screens.

# 7. PHASE SIX: ANIMATION, INTERACTION AND MICRO-DETAILS

Use motion to improve clarity, perceived responsiveness, and feedback.

Research the installed libraries and current documentation before selecting an implementation.

Consider React Native Reanimated or the platform's existing animation tools when appropriate. Avoid unnecessary additional dependencies.

## 7.1 Interaction states

Design consistent states for buttons, inputs, toggles, menus, dialogs, and interactive tokens.

Where applicable, implement:

- Default.
- Hover on web.
- Focus.
- Pressed.
- Selected.
- Disabled.
- Loading.
- Success.
- Error.

States must use consistent styling and accurate application data.

## 7.2 Motion principles

Use restrained, intentional transitions.

Examples include:

- A gentle appearance when gloss tokens arrive.
- Smooth movement when the layout changes.
- A clear transition between translation modes.
- Brief feedback when a button is pressed.
- A natural drawer or dialog transition.
- Appropriate feedback for recording and processing.
- Subtle changes in the avatar status display.

Use short, appropriate transitions, with approximately 150–280 ms as an initial guideline for ordinary micro-interactions.

Do not apply the same animation to everything.

Avoid excessive bouncing, persistent glowing, artificial cursor movement, repeated flashing, and decorative loops that consume resources.

Preserve the avatar's real animation timing.

Do not confuse a UI transition with a real avatar event.

## 7.3 Reduced motion and interruption

Respect the user's reduced-motion settings on supported platforms.

When motion is reduced, remove or simplify decorative movements while preserving essential state feedback.

Ensure animations do not block typing, selection, scrolling, translation submission, or playback controls.

Prevent duplicate event execution and cancellation problems.

### PHASE SIX EXIT GATE

# 8. PHASE SEVEN: ACCESSIBILITY AND INCLUSIVE DESIGN

Accessibility is a central product requirement, not an optional finishing touch.

Design for people with different visual, motor, hearing, language, and technical experience levels.

## 8.1 Screen readers and semantics

On native platforms, use appropriate accessibility labels, roles, hints, and state information.

On web, use correct HTML semantics, accessible names, keyboard navigation, and logical focus order.

Icon-only controls must have descriptive labels.

Mode selectors, microphone controls, playback controls, and autocomplete items must expose their actual state to assistive technology.

Avoid redundant announcements, confusing nested interactive elements, and inaccessible custom controls.

## 8.2 Contrast and text

Use sufficient text contrast and distinguishable control states.

Do not rely on color alone to represent recording, errors, success, the active translation token, or the selected mode.

Support text resizing and avoid clipping larger text.

Use plain language for loading states, permissions, errors, and recovery instructions.

## 8.3 Touch targets and keyboard access

Aim for approximately 44 points on iOS and 48 dp on Android for important interactive targets where practical.

Make controls usable without precise or repeated tapping.

On web, support keyboard operation and visible focus indicators.

Ensure dialogs and drawers have appropriate focus behavior and dismissal mechanisms.

## 8.4 Inclusive sign-language experience

Preserve the application's authentic sign-language content and translation workflow.

Do not substitute generic gestures, decorations, or ambiguous labels for meaningful signing information.

Provide textual context and feedback where appropriate.

Ensure essential actions do not depend exclusively on sound or color.

If language preferences, text-size settings, or additional accessibility preferences can be integrated properly, evaluate them without introducing unnecessary settings or unsupported features.

### PHASE SEVEN EXIT GATE

Accessibility must exist in the implemented controls, layouts, component APIs, and states. A written accessibility checklist alone does not satisfy this requirement.

# 9. PHASE EIGHT: FILE STRUCTURE AND IMPLEMENTATION RULES

Only after the audit, research, and design plan have been completed may you begin restructuring or creating implementation files.

## 9.1 Preserve architecture where it works

Do not rewrite everything for the sake of novelty.

Retain working services, existing contracts, valid shared hooks, navigation, state stores, API clients, and avatar integration.

## 9.2 Maintain a clean component structure

Organize the implementation according to actual responsibilities.

Potential responsibilities include:

- Main screen composition.
- Header.
- Avatar stage.
- WebView communication bridge.
- Translation composer.
- Word/sentence mode control.
- Gloss-token renderer.
- Playback controls.
- Recent-history presentation.

- Shared theme tokens.

Use the existing project structure and follow its conventions unless the audit reveals a genuine problem.

## 9.3 State management

Keep a consistent source of truth for shared translation state.

Avoid independently duplicated state for the current mode, input text, history, queue, and playback lifecycle.

Separate visual presentation from translation-processing and avatar-communication logic where useful.

Use appropriate types and preserve existing data contracts.

Avoid unnecessary state libraries or complicated abstraction layers.

## 9.4 Styling

## 9.5 Dependency and file management

1. Confirm the exact package name.
2. Read the official installation instructions.
3. Verify framework and version compatibility.
4. Check the peer dependencies.
5. Check whether the capability already exists in the codebase.
6. Confirm that the dependency is necessary.
7. Understand the required configuration changes.

Use the project's existing package manager and lockfile.

Do not install multiple alternative packages for the same problem.

Do not overwrite user work, delete unrelated files, or perform broad automated replacements without inspecting the effects.

Never expose private credentials or create unsafe client-side access to cloud resources.

# 10. PHASE NINE: PERFORMANCE AND PRODUCTION RELIABILITY

The result must run well on real devices, including less powerful phones.

## 10.1 Rendering and layout

Avoid unnecessary component remounts, unstable keys, expensive state propagation, excessive blur, uncontrolled animations, and needless re-renders.

Use FlatList or an appropriate virtualized web/native list when history size makes it beneficial.

Use memoization only where it provides a justified benefit.

Avoid overengineering a small application.

## 10.2 Keyboard and scrolling

Test multiline input, autocomplete, keyboard opening and closing, history scrolling, and dialogs.

Avoid nested scroll conflicts and controls hidden below the keyboard.

Make the composer stable across small screen heights and orientation changes.

## 10.3 WebView and animation reliability

Verify that typing, switching modes, and opening menus do not unnecessarily interrupt the avatar.

Protect the existing message protocol and asset-loading behavior.

Handle actual loading and error states.

Do not cause repeated WebView reloads, duplicate commands, queue corruption, or accidental replay.

## 10.4 Failure and recovery

Provide honest and helpful recovery behavior for genuine issues such as:

- Microphone permission denial.
- Speech recognition failure.
- Empty input.
- Invalid or unavailable translation.
- Missing animation assets.
- Network errors.
- Loading timeouts, where appropriately detected.
- Playback failure.
- No history available.

Do not add fake network status, fake progress, artificial success notifications, or retry buttons that cannot perform a real retry.
